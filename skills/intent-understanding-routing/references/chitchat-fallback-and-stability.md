# 闲聊、Fallback 与识别稳定性

## 为什么不要穷举闲聊

闲聊是开放集合：问候、情绪、生活分享、玩笑、测试、碎片输入、代码混写和无明确业务目的的表达都可能属于它。用有限 utterances 穷举会不断追长尾，增加路由延迟、维护成本和误拦截。

把有限、严格的高价值 utterances 留给业务意图；把闲聊当作“没有命中高价值业务路由后，经过风险门控的低成本路径”。

## 三种策略的正确用法

### 1. 语义描述替代穷举

语义描述适合 `DecisionRouter` 或结构化 LLM 解析器，因为边界需要用自然语言表达：

```text
属于日常问候、情绪表达、生活分享、寒暄或没有明确业务目标的闲聊。
不包含订单、退款、支付、账户、隐私、商品执行操作、投诉升级或人工转接请求。
即使用户语气轻松，只要包含业务实体或执行要求，也不属于闲聊。
```

如果使用 `IndexedRouter`，不要把这段描述直接当作相似度样本；应改写成用户口吻的 utterances，并用留出集验证。描述只改变决策模型的行为，不会自动改变 embedding 索引。

### 2. 排他性路由（NOT 决策）

推荐路径：

```text
输入
  -> 高精度 L0 规则
  -> 业务 Semantic Router
       -> 高置信业务路由：执行
       -> 无业务路由或低置信
            -> 风险门控
                 -> 有业务/安全信号：澄清、LLM 解析、人工或安全流程
                 -> 无业务/无风险：廉价闲聊模型
```

“NOT 决策”不是训练一个专门的“不是业务”模型，而是：

- 业务正路由保持严格阈值。
- 用 `None` 标签校准没有业务路由的置信度。
- 用风险规则/实体识别拦截不能安全归入闲聊的残差。
- 让低成本闲聊模型只处理真正的开放残差，并禁用它调用业务工具。

### 3. 混合路由

规则 + 语义 + 校准的组合通常比单层 embedding 更稳定：

- 规则层拦截“哈哈哈”“111”“测试”“停止”“转人工”等极高精度模式。
- 语义层处理口语化、近义改写和多语言表达。
- 稀疏特征处理订单号、商品型号、SKU、金额等精确 token。
- 结构化解析器处理多动作、槽位、否定和上下文指代。

规则必须是高精度，而不是“看到包含‘你好’就判闲聊”。像“你好，我的订单怎么回事”应保留业务信号，不能被问候规则截断。规则建议使用完整匹配、锚定模式、实体排除和长度限制，并保留命中原因。

## 风险门控

业务路由未命中后，至少检查：

- 是否包含订单号、商品 ID、SKU、手机号、地址、金额或其他业务实体。
- 是否包含退款、支付、账户、隐私、取消、删除、发送、修改等动作。
- 是否包含投诉升级、威胁、自伤/暴力/违法或人工转接信号。
- 当前会话是否存在待确认、待执行或已执行的任务。
- 请求是否来自高风险渠道、租户或用户权限范围。

命中风险信号时，不要直接进入闲聊。采用以下之一：

1. 缺失必要信息：提出一个最小澄清问题。
2. 语义尚可但边界模糊：交给 LLM 结构化解析或 DecisionRouter。
3. 高风险/低置信：转人工、拒绝执行或走安全策略。
4. 请求明确且安全：进入对应业务管线。

## 阈值与校准

- 未校准时，`confidence` 是 encoder 的原始相似度，不是概率。
- 先 `fit()` 再用业务成本选择阈值；至少使用独立测试集调用 `evaluate()`。
- 高风险路由使用更保守的路由级阈值，并由 Policy Engine 追加确认。
- 低风险查询可以追求更高 coverage；不可逆或资金操作要优先降低 false execution。
- 阈值变化、encoder 更换、语言扩展和路由重构后重新校准。
- 不要用正常流量中的已路由样本自评；需要覆盖未命中和错误路由。

## 其他稳定性手段

### 意图冲突的优先级

遇到同一句同时包含多个业务词时，先判断“用户是在咨询、查询状态，还是要求执行”：

1. 安全阻止、人工接管和明确的系统控制命令优先。
2. 知识/政策/资格问题不产生写动作。
3. 状态查询不会触发创建、取消、退款、发送等副作用。
4. 明确执行请求会产生动作，但必须通过 Policy Engine；高风险动作还要确认。
5. 同一句包含多个明确业务动作时保留全部动作，并生成依赖；不要用 top-1 标签覆盖。
6. 只有实体、没有动作时先澄清，不要猜测。

常见冲突：

- “退款到账了吗”是 `refund.status`；“我要退款”是 `refund.create`。
- “订单取消了吗”是状态查询；“取消订单”是写操作。
- “怎么取消订单”是 how-to；“取消订单 A123”是执行请求。
- “退款没到账”是退款进度；“订单没到”是物流状态。
- “不要发送”删除发送动作；“改成只发给采购经理”是上下文修改，不是新任务。
- “投诉物流”是人工/投诉信号，不应因为出现“物流”就自动执行物流查询。

### 输入归一化

处理空白、标点、emoji、大小写、繁简、全半角、重复字符、常见 ASR 错字和中英混写。保留订单号、商品型号、人名、金额等实体原值；不要用不可逆的全局清洗破坏精确 token。

多语言规则要显式覆盖，例如 `refund`、`refund status`、`check inventory`、`below warning level`、`create an Excel report`。中文关键字规则不能自动假设能覆盖英文流量。

### 硬负例与边界例

为每个易混淆路由准备：

- 正例。
- 邻近但不应命中的硬负例。
- 同时包含两个意图的复合例。
- 缺少实体、否定句和上下文省略例。
- 超范围、闲聊和混合混合输入。

硬负例用于评估和路由重构，不要把它们简单塞进某个正路由的 utterances 来“掩盖”边界问题。

### 多意图与上下文

- 对明显复合请求使用 `limit=None` 或多标签解析，不要强行只留一个标签。
- 由 DAG 判断动作依赖和审批顺序。
- 用 Context Resolver 处理“刚才那个”“第二个”“改成”“算了”“继续”。
- 新任务要能隔离旧槽位，避免长会话污染。
- 没有来源对象的发送请求必须澄清；只有上下文中存在 `last_output`、用户选中对象或明确附件时，才允许生成发送动作。

### 校准之外的分数信号

如果当前实现能取得完整候选分数，可把 top-2 margin、熵、与无路由校准结果结合，用作澄清触发信号；但必须验证它不会替代业务策略。不能取得完整分数时，不要假设 API 暴露了未文档化的字段。

### LLM 解析的保护

- 使用 JSON Schema/typed output，拒绝未知字段和不合法的动作。
- 提供有限的 pipeline/tool 枚举，不接受模型自由生成的执行目标。
- 把用户输入、检索文档和历史消息标记为数据，不当作系统指令。
- 解析失败、超时或 schema 不合法时回到澄清或安全降级，不默认执行。
- 对高风险模型输出做确定性的业务校验和权限校验。

### 版本与观测

每次 trace 至少记录：

- 路由、规则、编码器和索引版本。
- 候选路由及分数（遵守隐私和访问控制）。
- 是否校准、阈值、是否走 fallback、fallback 原因。
- 是否澄清、策略决策、是否执行和最终任务状态。
- 模型/prompt/schema 版本。

### 反模式

- 为每个长尾闲聊表达新增一条业务 utterance。
- 把 `name is None` 无条件当成闲聊。
- 用一个全局 confidence 决定资金、删除、发送等高风险操作。
- 用 LLM 自报“我很确定”代替校准。
- 用单个整体准确率掩盖某个高风险意图的低召回。
- 为了减少澄清率而放宽阈值，导致误执行。
- 让闲聊模型、检索模型或文档内容拥有工具权限。
