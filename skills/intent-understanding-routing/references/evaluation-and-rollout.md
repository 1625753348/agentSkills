# 评估、阈值选择与上线

## 数据集分层

评估集必须与 fit/训练 utterances 分离，至少包含：

- 每个业务意图的真实正例。
- 邻近路由的硬负例。
- 无业务意图的 `None` 样本。
- 闲聊、测试、情绪和碎片输入。
- 歧义、缺槽位、否定和超范围输入。
- 多意图、上下文修改、取消和话题切换。
- 安全、越权、提示注入和隐私相关切片。
- 错别字、繁简、方言、中英混写和 ASR 噪声。

建议用 JSONL 保留 `input`、`label`、`slice`、`risk`、`expected_action`、`context` 和 `notes`。不要把生产用户隐私直接放入评估集；先脱敏并做访问控制。

本 skill 提供一份可扩展的初始回归集 `assets/intent-routing-eval-cases.json`，覆盖 60 条路由、动作、风险、澄清、fallback 和上下文用例。它适合做接口契约和危险错误回归，不替代真实用户分布；新增线上错误时，应把脱敏后的最小复现加入对应切片。

## 指标

| 层 | 指标 |
|---|---|
| 意图 | Accuracy、Macro-F1、每路由 recall、hard-negative false positive |
| 槽位 | Slot F1、Exact Match、缺失槽位识别 |
| 路由 | Route Accuracy、coverage、abstention rate、clarification rate |
| 校准 | ECE、Brier score、reliability curve（按路由和风险切片） |
| 安全 | false execution rate、unsafe pass rate、越权率 |
| 执行 | Task Completion Rate、Tool Success Rate、重试/重复执行率 |
| 体验 | 首次响应 P50/P95、转人工率、用户纠正率 |
| 成本 | 每次成功任务成本、每路由平均调用数、fallback LLM 成本 |

整体准确率不能替代切片分析。高风险意图的漏召回通常比整体多 0.5 个百分点更值得优先修复。

## 阈值选择

阈值是业务成本函数，不是模型参数：

1. 校准后得到每个候选的 `RouteChoice.confidence`。
2. 在独立验证集上扫描阈值。
3. 对每个路由统计 TP、FP、FN、澄清和转人工。
4. 按业务成本选择：漏掉高价值请求、误执行副作用、增加一次澄清、转人工的成本并不相同。
5. 在最终测试集上验证；不要用用于选阈值的样本报告最终指标。

可以给不同路由设置不同的 `confidence_threshold`。高风险路由还应配置独立确认、Policy Engine 检查和人工审批，而不是只提高阈值。

## 离线验收

至少回答：

- 每个高价值意图的召回是否达到业务要求？
- 无业务路由的拒绝是否不会大量吞掉真实业务请求？
- 闲聊误拦截、闲聊误执行业务工具、误转人工的代价是否可接受？
- 复合请求是否保留了全部动作和依赖？
- 上下文修改是否只改目标字段？
- 否定、金额、订单号和实体是否保持正确？
- 更换 encoder 或阈值后能否解释性能变化？

## 上线阶段

建议按风险递增推进：

1. **P0 观测**：只记录路由建议，不自动执行；人工审阅误路由。
2. **P1 只读路由**：自动执行低风险查询和 RAG，保留人工回退。
3. **P2 受控写操作**：固定 Workflow、幂等和审批；只对已验证切片开放。
4. **P3 动态规划**：对有限工具集启用 Planner/Agent，设置最大动作数和预算。
5. **P4 持续优化**：基于反馈、漂移和 A/B 实验更新路由、阈值和解析器。

每一阶段都应有独立开关、按租户/流量比例的灰度、回滚和禁用自动执行的应急预案。

## 在线监控

重点告警：

- `None`/fallback 比例突变。
- 某路由置信度分布漂移。
- false execution、工具失败、重复执行和人工接管率上升。
- 澄清率上升但任务完成率下降（可能是路由边界退化）。
- 新编码器、prompt、schema 或索引版本上线后的分片差异。
- 高风险切片的路由和策略结果不一致。

对于标注反馈，不要只收集“用户是否满意”；要区分“路由错”“槽位错”“执行错”“回答错”和“用户改变主意”。

## 变更管理

- 路由名称是业务契约；重命名必须考虑 trace、指标、索引和下游 dispatcher。
- 路由、阈值、编码器、prompt 和 schema 都要版本化。
- 远程索引变更后确认校准器是否仍然有效；加载的校准器可能没有原始标注样本。
- 保存路由配置时不得写入密钥；从环境变量或密钥管理系统注入。
- 灰度期间新旧路由和 schema 必须可共存；回滚不能丢失任务状态。

## 最小发布闸门

发布前必须实际运行：

- 单元测试：规则、归一化、阈值优先级、fallback、schema、权限和幂等。
- 离线回放：真实/仿真流量上的混淆矩阵和风险切片。
- 故障注入：超时、异常编码器、索引不可用、JSON 解析失败、工具失败。
- 影子/灰度：与现有系统比较路由、执行和体验。
- 回滚演练：关闭自动执行、恢复旧路由、清理未完成任务。

未能运行的验证要明确报告为未验证，不能声称通过。
